# Security boundaries and limitations

The hosted Vercel demo uses iron-session authenticated/encrypted HttpOnly cookies, CSRF checks, server-side role/workspace checks, and private Blob data with conditional writes. Public demo credentials create browser-scoped demo identity rather than verified organizational identity. The server-only storage token derives the session password unless SESSION_SECRET is supplied. No token is sent to the browser. Clearing cookies loses the workspace reference; the demo has no account recovery or retention guarantee. Vercel Workflows runs bounded steps; provider calls remain at-least-once. The following Spring controls apply to the relational mode.

Implemented: Spring Security sessions with HttpOnly/SameSite cookies and CSRF; production JWT issuer/audience checks; workspace membership on sensitive operations; viewer write denial; tenant-scoped queries and foreign keys; optimistic revisions; immutable versions; input/graph/node output caps; process-local per-IP rate limits; bounded runtime and delays; field-name secret redaction; no user scripts; no generic outbound HTTP node; audit records and safe application errors. Passwords use Spring's BCrypt encoder.

Public local demo accounts are `demo`, `viewer`, and `other`, sharing the default `demo` password. `LOCAL_PASSWORD` overrides it. This profile is for isolated local demonstration and tests. Never expose it with private records. Production disables those accounts, enforces external JWTs, and sets Secure cookies. Browser OIDC authorization-code login, registration, verification, recovery, MFA, memberships administration, and shared session revocation are not implemented.

Field-name redaction covers nested token/password/secret/API-key/authorization/cookie names; it is not a general data-loss-prevention system. Do not put secrets into arbitrary strings or graph literals. Graph configuration is stored as provided. Tenant credential encryption, KMS integration, approved secret references, and full content redaction need implementation before credential-bearing connectors.

No HTTP node is exposed, avoiding an incomplete SSRF defense. Before enabling it, enforce DNS and redirect checks, IP pinning/network egress, private/reserved/metadata destination denial, protocol/size/timeout restrictions, and adversarial tests. User scripts need a separate sandbox and must never run in the API process.

AI calls have no tool access, use field-redacted input, require JSON output, and enforce time/output caps. Provider errors are sanitized. JSON mode validates JSON shape as an object, not a user-defined semantic schema. Live provider behavior and malformed provider-response tests remain incomplete. Provider calls may be repeated after a worker crash. Credentials are not exposed to the frontend.

Production work remaining: external identity browser flow; TLS/infrastructure validation; shared rate limits and sessions; PostgreSQL RLS evaluation; stronger role separation for publishing; durable usage accounting; comprehensive provider mocking; secret/dependency/container scan verification; content-security policy; incident response; backup drills; deletion/retention policies; security assessment. No compliance certification or penetration-test claim is made.
